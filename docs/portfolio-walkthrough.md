# 面试与源码讲解 / Portfolio walkthrough

讲清楚一个完整问题，比罗列 Agent、Workflow、A2UI 等名词更有说服力。以下内容是基于当前实现的讲解路线，不是对个人工作经历或业务规模的替代描述。

## 两分钟介绍

“我做的是 A2Flow：将 Agent 的工具调用、业务工作流和用户交互连起来。模型能根据请求选择已注册的能力；缺参时生成临时表单，用户提交后继续同一个任务。手动和定时执行的结果都有独立记录，用户可将异常带回对话继续处理，新的操作回执仍能关联到原异常。”

接着展示一次真实的完整链路：需求 → 执行/等待 → 提交 → 后续结果 → 刷新后的历史。现场没有配置和登录环境时，使用明确标记的 fixture 展示交互，不把它说成真实模型执行。

## 五个值得深入讲的问题

| 面试追问 | 真实设计与取舍 | 代码入口 |
| --- | --- | --- |
| 为什么不是直接接一个模型 API？ | SDK 负责模型循环；平台仍须解决资产授权、等待输入、任务状态、调度和真实业务结果。避免把模型文字当业务事实。 | `assembly.py`、`workflow_loader.py` |
| 提交表单怎么保证继续对任务？ | 保存并校验任务/node/interaction 身份，匹配 LangGraph interrupt，再通过原生 resume；普通聊天不隐式推进工作流。 | `langgraph_adapter.py`、`temporary_interaction.py` |
| 停止能撤回已执行操作吗？ | 不能。停止是禁止新准入与后续推进，已派发操作保留真实结果；业务补偿属于业务系统。 | `lifecycle.py`、`native_control.py` |
| 定时任务没有父对话怎么办？ | 执行结果是独立实体；用户显式引用保存结果到对话，后续处理建立关联任务。读取上下文不重跑业务。 | `chat/workflow_results.py`、B `processing_tasks.py` |
| 为什么仍保留 Java？ | 管理编写、发布和确定性校验是一类职责，模型执行是另一类。代价是多语言构建和跨服务装配，不能掩饰部署复杂度。 | `services/management-java/`、Python Runtime |

完整可点击代码入口见[当前架构](current-architecture.md)。

## 一个真实缺陷的讲法

图构建发生在 run 分配之后。此前失败处理只对已经创建的 graph 更新生命周期，导致构建失败时 run 留在 RUNNING，却出现失败事件。修复将生命周期失败更新移出 graph 存在判断，保留终态保护。定向验证覆盖：构建失败、执行失败、停止后晚到失败、成功后晚到失败；相同控制请求不会再次构建。

这比“我做了异常处理”更具体：能说明事务边界、失败窗口、修改位置和验证范围。另一个例子是 B 登录中同步 scrypt/数据库阻塞 asyncio 事件循环，改为框架已有有界 worker pool；但这并不等于完成防暴力破解限流。

## 演示清单

1. 说明演示是现场真实环境还是无密钥合成界面。
2. 展示一个带缺参的任务，确认等待时没有把任务标为完成。
3. 提交一次；说明后续是原任务继续，不是再启动一个 workflow。
4. 展示结果、运行时间、必要的业务回执；刷新后核对历史未重复执行。
5. 展示定时结果独立于 Chat 存在，以及显式引用/处理的关系。
6. 结束时说明哪些业务并未发生，例如草稿保存不等于审核通过或已发送。

## 不要夸大的地方

- 不说“任意 DAG/通用分布式调度”：当前产品是有界顺序节点。
- 不说“exactly-once”：区分平台控制去重与外部业务幂等。
- 不说“生产级高可用/万级并发”：没有相应公开压测和故障切换证据。
- 不说“全新机器一键自托管”：现有完整装配仍有初始化前提。
- 不把框架能力全部算作自己实现；讲清自己写了哪些适配、合同和状态边界。
- 不隐瞒 AI 辅助开发。展示自己能解释、审查和修复的具体代码与证据，不用提交数量代表能力。

## 下一步如何证明工程深度

优先做[质量路线图](quality-roadmap.md)中的完整干净部署、状态/事件原子发布和可重复故障验证。使用记录清楚的数据集和环境测量延迟、失败率与成本，再考虑规模宣传。不要先写没有来源的性能数字。
