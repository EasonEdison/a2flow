# ADR-0006：A2UI 工程化配置与模型入参契约

日期：2026-09-28
状态：用户已确认；本次仅记录方案，不表示代码、配置或公网已完成改造。

## 目的与背景

A2UI 的目的，是通过工程化固定组件、布局、样式、按钮及业务交互，只向模型开放必要的、受 AI 影响的参数，降低每次生成的结构和行为不确定性。不是让模型生成完整界面，再要求它自行保证正确。

当前稿件 Application 将完整 DataModel 字段均声明为模型必填参数，包括已有模板初始值的 export、confirmation 等状态。曾发生稿件保存成功，却因未传 export 初始对象而渲染失败。修复方向是明确参数职责，不是取消必要校验，也不是继续堆叠 Skill 提示词。

## 已确认规则

### 1. 展示与交互由配置确定

组件、布局、样式、按钮、Action 绑定由 M 端配置并发布。模型不能自由修改这些定义。标题、总结等确实需要 AI 生成的内容可以作为模型入参。

### 2. 一个字段只配置一个来源

字段来源可以是模型参数、常量、业务查询结果、系统上下文或用户输入，但同一绑定目标不配置多个竞争来源，不引入隐含优先级、多源覆盖或回退。

枚举是字段取值约束，不是新的来源类别。稿件 ID、版本等属于业务事实，通过查询、Action 绑定或系统传递；模型不得生成或猜测。模型可以按契约搬运先前真实查询结果，但这不使其成为事实权威，后端仍验证归属与版本。

Action 执行后按确定配置更新卡片，是既有交互行为，不是允许为一个输入字段配置多个来源。实现时区分调用入参绑定与后续状态更新，不把二者混为多源解析器。

### 3. 不新增供数模式开关

Skill 已查询商品列表，随后用 Application 修改某商品标题，可以直接使用已取得的数据。Application 用于展示列表及操作按钮时，可以配置 LoadBinding 查询并展示。

无需让编排者额外选择“模型供数”或“Application 自行查询”模式；沿用现有参数和绑定表达即可，也不强制全部改为只传 ID 后重复查询。

### 4. 模型通过查询、渲染两个工具使用 Application

先调用契约查询工具，再根据返回契约调用渲染工具。采用已讨论的统一查询入口：

```json
{"a2uiApplicationCodeList": ["example-application"]}
```

以上为 `query_skill_dependencies` 的 Application 查询参数示意。返回至少包含 appCode、用途、调用说明和模型入参 JSON Schema（paramsSchema）。Schema 明确字段类型、描述、必填、可选、枚举及适用约束；它不是完整 DataModel，也不要求模型填写布局、Action 或系统状态。

模型随后调用 `render_application`：

```json
{"appCode": "example-application", "params": {"title": "模型生成的标题"}}
```

示例不是具体资产的已发布契约。实际 params 必须遵循查询到的 Schema；不要求传齐所有可选项，更不要求传齐卡片所有内部字段。工具保持当前 Skill 绑定准入、可信 userId、环境及已发布配置读取边界。

### 5. 渲染及 Action 链路

后端校验模型入参，按已发布模板与绑定装配数据，执行已配置的 LoadBinding，将卡片事件发给前端，用户直接看到展示。

常量及明确初始状态由配置提供，不依赖模型重复传空对象；不得把 JSON Schema 的 default 擅自当成已实现的自动填值行为。业务查询失败不能静默改用模型猜测或默认业务数据。

用户操作由配置的 Action 取参并调用业务能力，结果经 ResultAdapter 更新卡片，不要求模型重新生成界面。交互模式、成功条件及完成标记决定是否等待、是否完成；渲染成功和模型输出结束不等于 Skill/Workflow 完成。

## 验收场景

- 标题由模型填写，常量文案和空导出初始状态无需模型传入，卡片仍正常渲染。
- 工具查询返回的 Schema 只包含模型调用参数，准确区分必填、可选及枚举；遗漏真正必填参数明确失败。
- 已查询到的商品 ID 可按契约传递；未查询到时不得由模型编造。
- LoadBinding 可自行取得列表并展示，无供数模式开关，无强制重复查询。
- 同一字段多源配置被拒绝，不依赖运行时覆盖顺序。
- Action 使用真实对象 ID、版本及系统 userId，结果更新原卡片；未执行确认不得伪造已确认状态。

## 替代方案与取舍

- 放弃“完整 DataModel 全部由模型填写”：易遗漏、重复搬运内部状态，削弱稳定性。
- 不采用独立供数模式分类：增加概念但不增加表达能力，现有绑定已能表达需求。
- 不通过放松所有校验解决问题：模型参数与业务身份仍需校验，只移除错误的职责分配。
- 工程化配置承担更多明确绑定，换取模型调用契约更小、界面行为更稳定。

## 与整体审查的关系及范围

本 ADR 替代审查报告中“需选择两种供数模式”及未定的 A2UI 参数边界讨论。宿主初始状态无需模型填写已获确认，具体实现应复用现有模板、LoadBinding、Action、ResultAdapter，不默认新增一套配置协议。
